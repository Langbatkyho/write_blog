---
name: deep-blog-writing
description: Run the seven-stage Deep Blog workflow from write_blog in Codex Cloud, preserving each stage and requiring author approval for the final article.
---

Use `flow/write_blog.yaml` and the selected `skills/deep/<style>/*.yaml` as the contract. Read `AGENTS.md` and `.agents/AGENTS.md` first. This Skill runs Deep mode only; do not use the Moment Skill or a Moment-only style. The author owns the final article.

1. Obtain the author's real notes and choose an existing Deep style, such as `reflective` or `provocative`. Save the notes in a UTF-8 input file outside `examples/`. From the repository root, call `python -m engine.cloud_stage_cli create --mode deep --style <style> --input <path> --output-root <safe-persistent-or-exportable-root>`. Preserve the returned run directory.
2. Call `python -m engine.cloud_stage_cli prepare --run-dir <run_dir>`. It returns the next stage, its opaque token, and its complete prompt. Give **only that prompt** to a fresh subagent for the stage. Wait for its response, save the exact response to a UTF-8 file for this attempt, then call `python -m engine.cloud_stage_cli submit --run-dir <run_dir> --stage-id <stage_id> --token <token> --response-file <path>`. Repeat sequentially until `prepare` returns `completed`. Never edit completed stage files. A rejected response can be corrected and submitted again with the same token.
3. For `reader_experience`, start a new subagent without inherited conversation or prior stage material when the agent runtime supports that option. Supply only the prompt returned by `prepare`; it contains the `writing_agent` draft and reader Skill, with no author input or earlier handoffs. Instruct this reader not to inspect repository files, checkpoints, logs, or other workspace content and not to edit or diagnose the draft. Check the prompt boundary before sending it. Shared workspace access means this is **context isolation**, not an enforced filesystem permission boundary; do not claim a guaranteed blind review.
4. For `editor_agent`, require `## Edited Blog` and `## Edit Log` inside `## Artifact`, followed by `## Handoff`. The engine splits these into `edited_blog.md` and `edit_log.md` and checks the edited article against the input's `desired_length` (default from the flow: 1200–1800 words) before saving the stage. Use `engine.parser.count_words()` for the deterministic count. If submission fails on length, ask that stage's agent to revise the response; do not advance to `coach_agent` or alter earlier stages.
5. After all seven stages, show `edited_blog.md`, `reader_report.md`, `coaching_report.md`, and `future_reflection.md` to the author. Once the author selects or edits the article, save that exact approved text in a separate file and call `python -m engine.cloud_stage_cli finalize --run-dir <run_dir> --approved-file <path>`. Verify `final_blog.md` against the approved file and preserve `run_log.md`. Return the two Markdown files separately when downloads work. If Codex web restricts download links to a read-only output directory, report that limit and provide each file's exact UTF-8 text separately, with SHA-256 and byte count for local saving and verification. Split a long log into numbered, unmodified chunks if necessary.
6. To resume in another Cloud task, export with `python -m engine.cloud_stage_cli export --run-dir <run_dir> --archive <archive.zip>` and import there with `python -m engine.cloud_stage_cli import --archive <archive.zip> --output-root <root>`. The user must transfer the ZIP; the final Markdown files alone do not contain the checkpoint. Verify the new task uses the same branch revision because flow and Skill YAML hashes are checked on resume.
